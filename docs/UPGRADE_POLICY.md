# Upgrade and External Multisig Policy

## Required authority separation

Production and production-like deployments MUST keep the program upgrade
authority separate from developer laptops, CI wallets, protocol guardians, and
ordinary operational roles. During the development and mainnet-maturation phase,
the expected arrangement is a reviewed external 2-of-3 multisig:

```text
Developer A ----\
Developer B ----- 2-of-3 multisig PDA ---> program upgrade authority
Security signer -/
```

The same external-signer abstraction may control a high-value vault, but the
program-upgrade multisig SHOULD be distinct from vault-operating multisigs. The
upgrade authority can replace all IronVault logic and therefore has total
custody impact regardless of the instruction-level permission model.

IronVault does not implement a production multisig. The test-only
`mock_multisig` program proves that a 2-of-3 external PDA can exercise the
ordinary signer interface through CPI. It is not audited, deployable governance
and MUST NOT be used outside tests. It is deliberately excluded from
`Anchor.toml`'s deployable program set and built separately only for LiteSVM. A
production deployment should use a
reviewed system such as [Squads program management](https://docs.squads.so/main/navigating-your-squad/developers-assets/programs).

## Bootstrap and authority transfer

1. Create the external multisig with three independently controlled members and
   a threshold of two. At least one member SHOULD use a separately stored
   security or hardware signer.
2. Record and independently compare the exact multisig vault PDA on two trusted
   displays.
3. Deploy from a dedicated bootstrap authority. Do not use a daily developer
   wallet.
4. Prefer Squads Safe Authority Transfer so the existing authority and multisig
   both approve the transition.
5. After finalization, run the read-only verifier in this repository. A release
   is blocked if it still reports a developer authority.
6. Remove and securely retire the bootstrap key only after the finalized
   authority and deployed bytes have been independently verified.

The pinned Solana CLI can transfer authority directly, but a multisig PDA cannot
sign the CLI's new-authority check. If Safe Authority Transfer is unavailable,
use the exact command generated by the reviewed multisig interface. The
`--skip-new-upgrade-authority-signer-check` option removes a safety check and
MUST be used only after independently verifying the destination PDA.

## Read-only deployment verification

After a deployment or upgrade, build the reviewed commit and run:

```bash
bash scripts/verify-upgrade-security.sh \
  --url <RPC_URL_OR_CLUSTER> \
  --program-id 2UWmTuefm4gqbfuZP36NSJMMSKLM4Rbop25jf1uBZAu1 \
  --expected-upgrade-authority <MULTISIG_VAULT_PDA> \
  --binary target/deploy/iron_vault.so
```

The verifier uses finalized RPC state and fails unless all of these are true:

- the returned program ID is exact;
- the account is owned by the upgradeable loader;
- a ProgramData account exists;
- the upgrade authority is exactly the expected multisig PDA;
- deployment slot and data length are structurally valid;
- `solana program dump` is byte-for-byte identical to the reviewed local SBF
  binary, with matching SHA-256.

The command is read-only. It does not prove the multisig's membership, threshold,
security practices, proposal contents, or review quality; those are external
governance facts that require independent evidence.

## Upgrade procedure

Every upgrade requires:

1. a reviewed commit and green full CI;
2. a reproducible SBF artifact and recorded SHA-256;
3. an upgrade proposal identifying program ID, commit, binary hash, buffer,
   release notes, migrations, and rollback constraints;
4. independent comparison of the proposed buffer bytes with the reviewed build;
5. at least two multisig approvals, including the designated security review;
6. execution and finalization;
7. the read-only verification above against the finalized cluster;
8. a post-upgrade smoke test and public evidence manifest.

CI and developer wallets may build or upload a buffer, but MUST NOT be able to
execute an upgrade by themselves.

## Immutability decision

IronVault remains upgradeable during development and mainnet maturation. Making
the program immutable is a separate, irreversible governance decision. Solana's
official deployment documentation uses:

```bash
solana program set-upgrade-authority <PROGRAM_ID> --final
```

Do not run this during ordinary release work. Once finalized, the program cannot
be upgraded or closed. If immutability is later approved, verify it by passing
`--expected-upgrade-authority immutable` to the read-only script and publish the
finalized transaction plus binary hash.

See the [official Solana deployment documentation](https://solana.com/docs/programs/deploying)
for the loader and authority lifecycle.
